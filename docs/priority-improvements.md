# 优先改进项

## 最值得先做的 5 件事

### 1. 停止把双开版当作整文件复制品维护

为什么最重要：

- 这是当前后端维护成本最高的点
- 最容易出现“单人版修了，双开版忘了改”
- 后续每次修 bug、调动作、加配置都要冒双份风险

当前表现：

- `backend/solo/luoke_macro_hotkey.py`
- `backend/double/luoke_macro_hotkey_double.py`

最好的下一步：

- 抽共享引擎
- 让双开版只保留变体差异

收益：

- 高

投入：

- 中

### 2. 把主后端文件按职责拆开

为什么重要：

- 现在一个文件同时承担了 Win32 调用、配置管理、运行时状态、加密、热键、宏执行和入口控制
- 这会让调试、阅读和安全修改越来越困难

最好的下一步：

- 先拆纯逻辑
- 再拆系统调用层
- 让入口文件尽量只负责“组装”

收益：

- 高

投入：

- 中到高

### 3. 给纯逻辑补上一层小测试

为什么重要：

- 当前几乎没有自动化回归保护
- 但配置规范化、状态文件、命令文件这些逻辑其实很适合先测起来

最好的下一步：

- 先测：
  - step 规范化
  - 配置序列化
  - 命令解析
  - `dry-run` 流程

收益：

- 高

投入：

- 低到中

### 4. 解决编码和文档可读性问题

为什么重要：

- 当前有些中文文案在不同环境下已经出现乱码
- 这会直接影响维护体验、协作体验和对打包结果的信心

最好的下一步：

- 统一 UTF-8
- 检查编辑器、终端、打包后显示链路
- 重写根目录 README，把运行和打包过程写清楚

收益：

- 中

投入：

- 低

### 5. 明确 Launcher 和 Backend 的协议

为什么重要：

- 现在文件通信方案本身是可行的
- 但状态 JSON 和命令 JSON 目前更像“隐式约定”，不是明确契约

最好的下一步：

- 文档化状态文件结构
- 文档化命令文件结构
- 条件允许时把共享字段定义集中一下

收益：

- 中到高

投入：

- 低到中

## 当前不建议优先做的事

在上面 5 件事动起来之前，下面这些先不用抢：

- 重新做一轮 UI 视觉改版
- 继续加更多脚本变体
- 把文件通信直接换成 socket 或命名管道
- 一上来就追求完整端到端自动化测试

## 接下来 3 次开发最推荐的顺序

### 第 1 次

- 抽共享后端辅助模块
- 降低单人版和双开版的重复代码

### 第 2 次

- 给纯逻辑补测试
- 文档化运行状态和命令协议

### 第 3 次

- 清理编码问题
- 更新 README 和打包说明

## 最划算的快速动作

如果只选一个“投入不大、收益最高”的动作，那就是：

- 暂时不改 launcher
- 暂时不改打包产物名
- 先抽 Python 的共享模块
- 让双开版逐步复用这些共享模块

这样能在不引入明显用户侧变化的前提下，把代码库的可维护性先明显拉起来。
